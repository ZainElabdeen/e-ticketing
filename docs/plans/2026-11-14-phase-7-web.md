# Phase 7 — Web App (Shop, Checkout, Backoffice) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Non-Claude agents (OpenCode): follow the tasks in order; every step is self-contained. Steps use checkbox (`- [ ]`) syntax for tracking. Claude implementers doing UI work also load the `frontend-design` skill (CLAUDE.md) and follow the Design System section below, which already settles the direction.

**Goal:** A React SPA (`apps/web`) that lets a shopper pick Gold/Premium/VIP tickets, create an order, pay by card or QR (with polling), see a receipt, and lets an admin sign in and view transactions, ledger entries, account balances and ticket availability. Every call goes through the Gateway; there is no mock data.

**Architecture:**

- **Stack.** Vite + React + TypeScript, served by nginx in its own container.
- **API layer.** One typed API layer: `openapi-fetch` over the generated `Gateway.paths` types. It sits behind a React context, so tests inject a stub `fetch`.
- **Server state.** TanStack Query holds server state, React Router maps the six routes of spec §5, and React Hook Form + Zod handle the two forms.
- **Origin.** The browser always calls the relative base `/api`:
  - Vite's dev server proxies `/api` to the Gateway;
  - in compose, nginx proxies `/api/` to `gateway:3000` with the prefix stripped;
  - in K3s (Phase 9), Traefik does the same.
- **No CORS.** The page and the API share one origin, so no CORS is involved.

**Decisions taken for this plan (2026-11-14, by the user):**

1. **Same origin.** In compose, the web container's nginx proxies `/api/*` to the Gateway with the prefix stripped, mirroring the K3s ingress. The SPA build uses `/api` everywhere.
2. **Tests stub `fetch`.** Component tests pass a stub `fetch` into the API client. No MSW.
3. **No browser E2E package.** Component tests plus the backend smoke cover the flows. At the end of the phase the controller runs the real flows (card, QR, backoffice) in a browser and reports.
4. **Visual direction: ticket-stub editorial.** See the Design System section.
5. **Resume after a 409.** After a 409 `PAYMENT_IN_PROGRESS` / `ORDER_ALREADY_PAID`, the SPA finds the payment from its own sessionStorage memory (orderId → paymentId, saved on every 201). The error envelope carries no paymentId. With nothing remembered, it says the payment is running elsewhere and polls the order.

## Global Constraints

- Node 26, pnpm 10.34.9 workspaces, Turborepo. The package name is `@eticket/web`, ESM (`"type": "module"`). Pin dependency versions exactly (no `^`/`~`).
- **No UI framework.** Use CSS Modules (`*.module.css`) plus one global `tokens.css`, and no inline `style={…}` props: nginx sends a CSP without `'unsafe-inline'` for styles.
- **Wire types come only from `@eticket/contracts`** (`Gateway.paths`). Never hand-write a duplicate of a contract schema. Small UI-only types are fine.
- **Server strings are rendered as text.** `dangerouslySetInnerHTML` is forbidden.
- **The API base URL is `import.meta.env.VITE_API_BASE_URL ?? '/api'`.** No absolute gateway URL appears in the bundle.
- **Money arrives in integer minor units** plus a `currency` code. Format with `Intl.NumberFormat`; never divide into floats for arithmetic. Totals are computed in minor units.
- **The server total is authoritative.** The total on `/` is a preview from listed prices; checkout and the result page show the server's `totalMinor` / `amountMinor`.
- **The browser never holds an API key.** Only the backoffice JWT is held: in memory plus `sessionStorage` key `eticket.backoffice.session`, never cookies or localStorage. `Authorization: Bearer` is sent only on `/v1/backoffice/*`.
- **A 401 means "session ended" only on `/v1/backoffice/*`.** On shop routes a 401/403 never happens: the Gateway maps a downstream key problem to 502. Shop errors use the §5 table.

## Design System (ticket-stub editorial)

**Subject:** a ticket counter for one event, used by shoppers buying 1–10 tickets, and a back room where an admin checks the books. The memorable thing is the ticket stub: a perforated card with two half-circle notches. Everything else stays quiet.

**Color tokens** (`apps/web/src/styles/tokens.css`, as CSS custom properties on `:root`):

| Token | Hex | Use |
| --- | --- | --- |
| `--paper` | `#F6F1E7` | Page background (ticket stock) |
| `--card` | `#FFFDF8` | Stub and table surface |
| `--ink` | `#1B1F2A` | Text, rules, and the stub outline. A blue-black like ticket ink, not tinted grey-black |
| `--ink-muted` | `#5D6270` | Secondary text |
| `--rule` | `#D8CFBE` | Hairlines, perforation dashes, table borders |
| `--stamp` | `#D7321B` | The single accent: primary buttons, focus ring, the PAID stamp, errors |
| `--tier-gold` / `--tier-premium` / `--tier-vip` | `#B8902F` / `#4F6475` / `#6E2B4F` | Only as a 6 px band on the left edge of each stub |
| `--ok` | `#2F6B3F` | "Balanced" on the accounts tab and "Succeeded" status text |

No gradients and no box shadows. Depth comes from a 1.5 px `--ink` outline on stubs and `--rule` hairlines elsewhere.

**Type:** one family, Archivo Variable (`@fontsource-variable/archivo`), self-hosted by Vite with no CDN.

- Import `@fontsource-variable/archivo/wdth.css` if the package ships it (full `wdth` + `wght` axes). Otherwise import the default entry and drop the width settings.
- Display text (ticket names, page titles, amounts on stubs and the receipt) uses `font-stretch: 75%` (condensed) and weight 700.
- Body text uses width 100% and weight 400/500.
- All numbers use `font-variant-numeric: tabular-nums`.
- Scale (rem, 16 px base): 0.875 / 1 / 1.25 / 1.75 / 2.5 / 3.5. Line height is 1.5 for body and 1.1 for display.
- Body line length is at most 68ch.

**Layout:** content is left-aligned in a single column, max width 880 px, with a 16 px side gutter on mobile and 32 px on desktop. Wireframes (desktop):

- **Receipt.** A narrow column with a zigzag torn bottom edge (CSS `mask` with `conic-gradient`).
- **The one motion.** On the result page, the "PAID" stamp rotates in from −8° and 1.3× scale to −4° and 1×, over 280 ms. It is skipped under `prefers-reduced-motion`. There are no hover animations on cards and no entrance fades.

- **Shop:** headline "Pick your tickets"; each stub shows "{n} left" ("Sold out" at 0).
- **Checkout:**

- **QR page:** "Scan to pay"; status "Waiting for payment…"; after 60 s "Still processing" with the button "Check again".
- **Result:** "Payment received".
- **Errors:** use the §5 table wording exactly. The generic banner reads "Something went wrong on our side. Try again."

## Review Focus

1. **Reload or deep link mid-flow.** `/checkout/:orderId`, `/checkout/:orderId/qr/:paymentId` and `/result/:paymentId` must work from the URL alone (fresh `QueryClient`, empty memory). The SPA fallback in nginx must serve `index.html` for them. Tests: Task 3 "checkout loads from the URL alone"; Task 4 "QR page loads from the URL alone"; Task 7 smoke step "deep link returns index.html".
2. **Double submit.** A double-click on Pay or Checkout sends exactly one POST: the button is disabled while the mutation is pending. Tests: Task 2 "checkout button sends one order on double click"; Task 3 "pay sends one payment on double click".
3. **Expiry while the user is on the page.** The countdown reaching zero disables Pay and shows "Start over", even with a filled card form. A QR page whose order expires stops polling once the payment is CANCELLED, or once a GET shows the order is no longer payable. Tests: Task 3 "countdown at zero disables pay"; Task 4 "polling stops on cancelled".
4. **Polling under pressure.** A 429 or 5xx during QR polling must not end polling or show an error page: keep polling and add a quiet "Reconnecting…" line. Polling pauses in a hidden tab, and the 60 s cap does not count hidden time. Tests: Task 4 "polling survives a 429" and "polling pauses while hidden".
5. **Money and numbers at the edges.**
   - Large minor amounts format exactly (`formatMinor(123456789, 'AED')`).
   - Quantity steppers never exceed `min(10, available)` or go below 0.
   - A sold-out type has its stepper disabled.

   Tests: Task 1 `formatMinor` cases; Task 2 "stepper respects availability".

- **`renderWithApp` defaults.** It wraps the UI in `ApiProvider` (using the stub fetch), a fresh `QueryClient` (retries off), `AuthProvider` (from Task 6; until then a no-op) and a `MemoryRouter` at `route`.

**`submitPayment` (spec §5 key lifecycle):**

- It sends `Idempotency-Key: key`.
- On `NETWORK_ERROR` or status ≥ 500 it retries **with the same key**, up to 2 more times, with sleeps of 500 ms then 1000 ms.
- On 422 `IDEMPOTENCY_KEY_REUSE` it makes **one** new key and resubmits once. It returns the key actually used.
- Every other error is thrown unchanged (an `ApiError`).

  - `RATE_LIMITED` → the rate-limit banner.
  - `UPSTREAM_*`, `INTERNAL_ERROR` or `NETWORK_ERROR` → the generic banner.

```ts
export type PollState = 'polling' | 'succeeded' | 'cancelled' | 'timeout';
```

**Polling rules:**

- Use `useQuery` on `GET /v1/payments/{id}` with `refetchInterval` set to `intervalMs` (default 1000) while `state === 'polling'`, and `refetchIntervalInBackground: false`.
- The cap is `maxVisibleMs` (default 60 000). It counts only time while `document.visibilityState === 'visible'`; when it is reached, `state = 'timeout'`.
- `SUCCEEDED` → `'succeeded'`; `CANCELLED` → `'cancelled'`.
- An error (429, 5xx or network) sets `reconnecting: true` and keeps polling. On a 429, wait at least `retryAfterSeconds`.
- The next success clears `reconnecting`.
- `restart()` resets the cap and resumes.

- `succeeded` → `navigate('/result/'+id, { replace: true })`.

- `timeout` → "Still processing" plus "Check again" (calls `restart`).
