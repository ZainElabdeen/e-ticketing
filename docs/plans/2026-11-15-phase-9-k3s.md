# Phase 9 — K3s Deployment, Deploy Guide and README Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The whole stack (Postgres, 4 services, web) runs on any single-node K3s VM (amd64 or arm64) behind Traefik with Let's Encrypt TLS, deployed from the GHCR images by a script or by an opt-in CD job; CI proves the manifests in a real K3s cluster (k3d); the README and `infra/k8s/README.md` explain the system, local run, deploy, env vars, API examples and trade-offs.

**Architecture:** Kustomize base in `infra/k8s/base` plus two overlays: `local` (k3d in CI and on a laptop: locally built images, plain HTTP) and `prod` (generated on the VM from a git-ignored `infra/k8s/.env`: hostname, ACME email, image tag, TLS). Secrets never live in git: `setup-local.mjs` generates them on the VM into `infra/k8s/.env`, and `apply-secrets.sh` turns them into one Kubernetes Secret. Postgres bootstraps roles through `docker-entrypoint-initdb.d` (same script as compose) and every DB service runs its migration image as an initContainer. Traefik routes `/api/*` to the gateway (prefix stripped, outer rate limit) and everything else to web.

**Tech Stack:** K3s (Traefik v3 bundled), Kustomize (built into `kubectl`), k3d (CI and local), kubeconform (CI), GitHub Actions, GHCR, DuckDNS (or any DNS name), Postgres 18.

**Spec:** `docs/spec.md` §9 Deployment, §12 Deliverable documentation, §7.1 env vars, §10 risks; ADR-0011; `docs/PROMPT.md` Phase 9; `docs/engineering/initial-assessment.md` (M5, L14, L15, L17, L18).

**Branch:** `phase-9-k3s` from `dev` (already created; first commit `18f23c9` carries the .NET S8949 fix that missed PR #2). Merges to `dev`, then release PR `dev` → `main`.

## Decisions taken with the user (2026-11-15)

1. **Secrets:** generated on the VM by `setup-local.mjs --env infra/k8s/.env`, applied with `kubectl create secret … --from-env-file`. Nothing secret in git; `ADMIN_PASSWORD_DEV` never enters the cluster (spec §7.1).
2. **Deploy:** an opt-in GitHub Actions CD job (`deploy.yml`) runs after `Images` succeeds on `main`: SSH to the VM, check out the commit, run `infra/k8s/scripts/deploy.sh`. It skips (green) when the `DEPLOY_*` secrets are absent. The same script is the manual path.
3. **Testing without the real VM:** kubeconform validates rendered manifests in `verify`; a new `k3d` CI job boots K3s, deploys the `local` overlay with locally built images, and runs the smoke test and the gateway contract suite through the ingress.
4. **Host:** not chosen yet (Oracle Cloud A1 or Google Cloud are both possible). Manifests and guide are host-agnostic: any Linux VM with ≥ 2 vCPU / 4 GB, amd64 or arm64, ports 80/443 open. ADR-0026 amends ADR-0011's "Oracle only".

## Rulings in this plan (record in ADR-0026)

- **Postgres bootstrap via `docker-entrypoint-initdb.d`, not a Job.** Spec §9 says "Job before services", but `00-roles.sh` is not re-runnable (`CREATE ROLE` fails twice) and a Job's pod template is immutable on re-apply. initdb runs once on an empty volume, exactly like compose. Cost if wrong: a password rotation needs a manual `ALTER ROLE` (documented in the guide).
- **Migrations as an initContainer of each DB service, not a Job.** Same image (`migrate-<schema>`), same `MIGRATION_DATABASE_URL`; the service pod starts only after `migrate deploy` exits 0, and a new image tag re-runs it on every rollout. Prisma takes an advisory lock, so a second replica is safe. Cost if wrong: migration logs live in the pod's init container (`kubectl logs <pod> -c migrate`).
- **Every image gets every `sha-<7>` tag.** `images.yml` builds only changed images; on `main` it now re-tags each unchanged image from `latest` to the new `sha-<7>` (registry-side `imagetools create`, no rebuild), so a deploy pins all eight images to one commit.
- **Client IP:** Traefik's Service gets `externalTrafficPolicy: Local` (HelmChartConfig) so Traefik sees the real client IP; the gateway trusts one hop (`TRUST_PROXY=1`).

## Global Constraints

- Never commit secrets; never read or print `infra/.env` or `infra/k8s/.env`. Both are git-ignored. Scripts load env files with `node --env-file` or `--from-env-file`, never shell `source`.
- Namespace `eticketing`. Image names `ghcr.io/zainelabdeen/e-ticketing/<image>` with the eight names in `.github/images.json`; `prod` tags `sha-<7>`, never `latest`.
- Service ports and names as compose: `postgres:5432`, `ticket-service:3001`, `payment-service:3002`, `ledger-service:3003`, `gateway:3000`, `web:8080`. Only Traefik is exposed; every Service is `ClusterIP`.
- Env values per service exactly as `infra/docker-compose.yml`, except: `TRUST_PROXY: '1'`, `WEB_ORIGIN: https://<host>` (local overlay `http://localhost:8081`), `SWAGGER_ENABLED: 'false'` in prod. `RATE_LIMIT_WINDOW_MS` and `ADMIN_PASSWORD_DEV` never appear in any manifest.
- `DATABASE_URL` / `MIGRATION_DATABASE_URL` are built in the manifest with `$(VAR)` interpolation from Secret-backed env vars defined earlier in the same container; no URL with a password is stored anywhere.
- Probes: liveness `GET /health/live`, readiness `GET /health/ready` (web: `/healthz`). The ticket-service `terminationGracePeriodSeconds: 20` (as compose `stop_grace_period`).
- Containers: `runAsNonRoot: true`, `allowPrivilegeEscalation: false`, capabilities drop `ALL`; requests/limits set; one replica each (spec §10: jobs assume one replica).
- No new dependency except k3d and kubeconform (CI binaries, pinned version + sha256) and the GitHub Actions already used. Pin every action to a commit SHA with a version comment (ADR-0025).
- Contract suite order rule still applies; in the k3d job only the gateway suite and the smoke test run (the service ports are not exposed).
- Commits: conventional, small, end with the session's `Co-Authored-By` line.

## Review Focus

1. **Rate limits collapse to one bucket behind Traefik.** If Traefik's Service keeps `externalTrafficPolicy: Cluster`, every client arrives from a node IP and one user exhausts `orders`/`login` for all. Expect: two requests with different source IPs get separate buckets. Task 2 asserts the HelmChartConfig and `TRUST_PROXY=1` in the rendered output; Task 4's k3d job proves a spoofed `X-Forwarded-For` cannot escape the login limit.
2. **A secret value with a character `--from-env-file` or a URL mangles.** Owner passwords go unencoded into `postgresql://` URLs. Expect: `apply-secrets.sh` rejects any value outside `[A-Za-z0-9._~-]` for `*_PASSWORD` keys before applying. Task 3 tests it.
3. **`ADMIN_PASSWORD_DEV` or `GATEWAY_HOST_PORT`-style local keys leak into the cluster Secret.** Expect: the Secret holds exactly the allow-listed keys. Task 3 tests the filter.
4. **Rollout pins a tag that does not exist for an unchanged image** (ImagePullBackOff). Expect: after a `main` push that changes one app, all eight images have `sha-<7>`. Task 5 tests the retag selection script; `deploy.sh` checks every image tag exists before applying.
5. **Re-running deploy on a live cluster wipes or re-bootstraps data.** Expect: second `deploy.sh` run is a no-op for Postgres (StatefulSet PVC kept, initdb not re-run), migrations report "No pending migrations". Task 4's k3d job deploys twice.
